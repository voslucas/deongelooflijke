# Codex repository reference

Repository context for future work on Ongelooflijk Archief, the unofficial Dutch archive of De Ongelooflijke Podcast. Reviewed on 22 November 2026 against the working tree at commit `8846383`, including the existing uncommitted changes.

The deployed build is a static multi-page website generated by `scripts/5b_build_site.py`. The older single-page app still exists and supplies the static site's base CSS. Several existing documents describe earlier implementation stages; use the distinctions below when choosing files and commands.

### Production page and transcript flow

`SiteData` loads split episodes and aggregates, master bios, guest overrides, and staged book/person details. Python emits page content; `page_shell` supplies navigation, metadata, analytics, and `/assets/app.js`. The main element's `data-page` chooses which browser initializer runs.

Episode pages embed key, duration, MP3 and NPO URL in `#ep-meta`. On page initialization, `app.js` fetches `/data/transcripts/{key}.json`, resolves speaker IDs through `speakers[]`, computes statistics, and fills the transcript, river, speaker legend, and Analyse tab. Summary, chapters, highlights and sidebar entities already come from Python-rendered analysis data. The player exposes `window._PL`, supports seeking and rates 1, 1.5 and 2, and follows the active transcript segment and chapter.

The older app instead loads full episode details before fetching a transcript and overlays `e.an` into the raw transcript before `buildTFromRaw`. Its caches and calculations are independent of `app.js`.

Episode “Woordenschat” uses the same filtered type-token ratio in both versions: lowercase letter tokens (including accented letters and internal hyphens), longer than three letters, excluding the SPA `STOP` list. Divide unique remaining words by all remaining word occurrences per speaker, round to three decimals, then display whole percentages on a fixed 0–100% scale. This is a content-word measure and depends on how much someone speaks. The static tokenizer/list in `app.js` mirrors `tok`/`STOP` in the template; `tests/test_vocabulary.py` verifies parity against available transcripts using Node.js.

## Data contracts

### Episode identity and master records

`scripts/utils.py:ep_key` returns a numbered episode as a string, or `x` followed by the NPO `id` for an unnumbered episode. Current unnumbered keys are `x5005` and `x133821`. Feed snapshots use `npo` for the corresponding source ID; master episodes use `id`.

The master object is `{eps: [...], bios: {...}, built: ...}`. Episode fields are `n` number, `t` title, `d` ISO publication date, `s` duration seconds, `x` description, `r` maker recommendations, `id`/`sl` NPO identifier/slug, `g` guests, `p` Stefan Paas presence, `th` themes, `f` format, `q` description quotes, and `mp3` audio URL. Older examples include `sj`, which stage 3 currently does not produce.

Stage 4 writes full episode records with `kw` and optional `an`. Nonempty analysis `guests` and `themes` override `g` and `th` in split output, without updating the master. Empty lists do not clear the fallback values.

### Transcripts and speaker identity

Transcripts have `episode`, `source`, `speakers`, `segments`, `events`, and initially empty summary/analysis containers. Segments use seconds in `{start, end, speaker, text}`. Their speaker references point to IDs such as `S1`, not names.

Treat `speakers[]` in `data/transcripts/{key}.json` as the current identity source. Do not assume `S1` is David: episode 327 currently has David as S2, Stefan as S3, and Kader Abdolah as S1, with no explicit roles. New transcription output uses Dutch roles `Presentator`, `Vaste gast`, and `Gast`; existing records can omit roles.

Initial Azure naming is a word-count heuristic capped at expected cast size. Voice identification can subsequently rename clusters in place. Voice profiles are normalized embeddings stored under slugged names. Name reconstruction from profile filenames title-cases name particles, so matching is case-insensitive.

The transcription code synthesizes `overlap` events for speaker switches with a gap below 300 ms. These are heuristic transitions; laughter detection is not implemented. The older real transcript view explicitly uses empty laughs and zero interruptions.

### Analysis and enrichment

Analysis remains separate in `data/analysis/{key}.json`. Relevant fields include `summary_tldr`, `summary_points`, `chapters`, `highlights`, `bible_refs`, `themes`, `guests`, `people`, `books`, `places`, `quotes`, `keywords`, and `similar`, plus model/date/usage metadata.

- `people[]` includes canonical name, note, first mention time, estimated `mention_count`, and optional `wiki_*` enrichment.
- `books[]` includes title/author/note/time and optionally canonical names, ISBNs, volume ID, and thumbnail.
- `bible_refs[]` contains actual citations with optional `start_seconds`, not generic Bible mentions.
- `similar[]` contains recommended episode numbers with Dutch reasons; static rendering uses those numbers and falls back to keyword overlap.
- Stage 4 subtracts five seconds, floored at zero, from people, books, chapters and highlights in the served analysis copy. It does not shift Bible references or source analysis files.

The analysis script defaults to the literal model string `claude-sonnet-5-5`, uses 8,000 output tokens, and truncates timestamped transcript text at 60,000 characters. Book verification and similar-episode selection make additional model calls unless disabled. Model strings and cost comments are repository configuration; check service support and pricing before future API work.

### Guests and mentioned figures

`data/persons/{slug}.json` holds actual guest overrides such as `socials` and `bio`; portraits live in `data/persons/images/`. Per-person bio takes precedence over master `bios`. The static renderer expects portrait URLs ending in `.jpg`; builders rename `.jfif` on copying but preserve `.png`, `.jpeg` and `.webp` filenames.

`data/persons_mentioned/{slug}.json` is generated from analysis people. It contains name, slug, unique notes and the selected Wikipedia record, preferring Dutch over English and then images within a language. These files are distinct from guest profiles even when someone belongs to both groups.

Mention aggregates combine transcript mentions with analysis people/books/places. Fields include `n` display name, `c` category, `k` normalized key, `x` count, `eps`, `sp`, `yr`, and `mx` total mentions. In the analysis path, `x` counts episode entries while people `mx` sums mention estimates. Transcript counts and merge semantics differ; do not treat all counts as exact spoken-name occurrences. Analysis people aggregates currently have empty timestamp hits, while book aggregates carry first-discussion times.

### Books and Bible text

Book detail keys prefer ISBN-13, otherwise `vol-{volume_id}`. Enrichment may discover an ISBN and save under a different key; the static loader also registers volume-ID aliases. `book_covers.py` downloads covers at build time using Open Library by ISBN, then selected Google Books covers; both renderers use local JPEGs or a gold icon. The JPEGs and identity manifest in `data/book_covers/` are versioned in Git. Builds still find missing covers, and the daily new-episode workflow includes newly downloaded covers in its data commit. See `docs/book-covers.md`. Book buying links use an existing bol.com affiliate URL. HTML descriptions are sanitized during enrichment and rendered as plain text by the static builder.

Bible source files use OSIS book codes and string chapter/verse keys. Builders collect referenced passages into three-verse snippets. The older app embeds these as `bvdata`; the static app fetches `/data/bvdata.json`. Bible reference parsers are duplicated and have differing accent/alias support.

## Build and verification commands

Run from the repository root. The existing Windows environment is `.venv` with Python 3.12.1. Use its executable explicitly because Claude-specific activation hooks do not configure Codex shell calls. Commands below are separate PowerShell commands; stop if any stage fails.

### Static build with all runtime data staged

```powershell
.\.venv\Scripts\python.exe scripts/4_split_data.py
.\.venv\Scripts\python.exe scripts/5_build_site.py
.\.venv\Scripts\python.exe scripts/5b_build_site.py
.\.venv\Scripts\python.exe -m http.server 8787 --directory site/static
```

Open `http://localhost:8787/`. The middle step builds the older app as well, but currently provides the implemented staging path for transcripts, mentioned-person details, and word index. Once those files are already current in `site/dist/data`, a static-only markup or `app.js` change needs only `5b_build_site.py`. Re-run stage 4 when analysis or master data changes, and re-stage runtime sources when those change.

`--clean` is unnecessary for routine edits. Before using it, check that the resolved output path is the intended generated directory. Builders otherwise overwrite generated files without comprehensively removing obsolete output.

### Feed and episode processing

Stage 1 reads an existing `data/raw/feed.xml`. The workflows download it from the Omny feed URL recorded in `.github/workflows/*.yml`; older docs show an NPO URL. After updating the XML, run stages 1, 2 and 3 in order. Stage 3 rewrites the master, including fallback bios and its fixed built date.

For a newly available episode, the processing order is:

1. Refresh the feed and master metadata.
2. Transcribe the episode; retain audio until any voice identification work is complete.
3. Identify speakers against profiles, inspect uncertain assignments, and apply appropriate corrections.
4. Run `analyze_episode.py --episode N`.
5. Run `8_enrich_people_wiki.py --episode N`.
6. Run `9_enrich_books_detail.py --all-missing`.
7. Run `10_collect_persons.py`.
8. Generate missing guest biographies with `enrich_guest_bios.py --all-missing`.
9. Update the word index if transcript data changed, then split, stage and build the site.

Use `--force` deliberately when reanalyzing an existing episode. Reanalysis replaces its source analysis, so rerun downstream enrichment and collection. Biography generation uses master guest membership; guests discovered only by the stage-4 analysis overlay may need master metadata reconciliation first.

### Dependencies and credentials

`requirements.txt` covers HTTP clients, Anthropic, spaCy, numpy and voice tooling. Install a Dutch spaCy model separately; model loading tries large, medium, then small. Playwright/Chromium for scraping, Pillow/Tkinter for the editor, and pytest for tests are additional prerequisites. The test files also work with standard-library unittest discovery.

Azure uses `AZURE_SPEECH_KEY` and `AZURE_SPEECH_ENDPOINT`. Model scripts generally accept `ANTHROPIC_API_KEY` or `CLAUDE_API_KEY`. `GOOGLE_BOOKS_API_KEY` is optional. `.env` parsing differs between scripts, including quote stripping, so follow the specific implementation when diagnosing authentication.

## Design and content rules to preserve

`CLAUDE.md` remains the detailed coding/design guide. Its main visual rules apply to both implementations even where its architectural description is older.

- Dutch interface copy; full name De Ongelooflijke Podcast on first use. David is the presentator and Stefan the vaste gast.
- Warm parchment, dark ink, gold for data, violet for interactions. Use existing tokens, synchronize dark modes, and keep gold text dark brown.
- Lora for headings and names, Spectral for prose, system UI for controls, metadata and numbers. Use tabular digits for timestamps and data.
- Maximum content width 1120 px, detail sidebar 300 px, stacked under 900 px. Use borders and flat panels, with mobile tables in scroll wrappers.
- Speaker colors: David ink, Stefan gold-deep, guests violet, teal, rose in order.
- Escape data before HTML interpolation; preserve the limited safe-description HTML handling where used.
- Use real buttons and links, visible violet focus, reduced-motion support and both light and dark themes. Keep simulated data explicitly labeled.
- Use the existing saint artwork without recoloring or cropping its halo. Actual builder asset paths are `design-system/assets/logos/logo360.jpg` and `wordmark672.png`.
